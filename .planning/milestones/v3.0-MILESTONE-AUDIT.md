## Intent Satisfaction

### Core Ask (a) — Provider-Agnostic Advisor

**Verdict: SATISFIED**

A uniform `Provider` protocol (`python/fdars/advisor/providers/_protocol.py`) defines
`complete_structured(schema, messages, system)`, `name`, `model`, and
`supports_native_structured_output`. All four backends (Anthropic, OpenAI, Gemini, Ollama)
implement this protocol as separate adapters with no shared state. The protocol is
`@runtime_checkable`, enabling duck-typed fakes in tests.

The grounding invariant holds on **every** backend: `_check_grounding` is called inside
`advise()` in `python/fdars/advisor/__init__.py` (line 443), **after** `p.complete_structured()`
returns and **not** inside any adapter. This was confirmed by injecting a fabricating
`FakeNativeProvider` — `GroundingViolationError` was raised correctly with:
`"Evidence item cites value '99.99' not found in diagnostics"`.

Validate-and-retry (`ValidateAndRetry` in `_validate.py`) wraps all providers. Native-SO
providers (Anthropic, OpenAI, Gemini) bypass the repair loop; non-native (Ollama) gets up to
2 retries with a re-included diagnostics message, then a deterministic `ValueError`.

Local/offline path: `OllamaProvider` takes no API key, uses `ollama.chat()` with `format=`
for schema-constrained output, and `supports_native_structured_output = False` routes it
through the retry path. No SDK imported at module load; `import fdars` confirmed SDK-free.

Provider/model selection: `resolve_provider()` in `_factory.py` enforces precedence:
explicit `provider=` arg > `FDARS_ADVISOR_PROVIDER` env > default (`"anthropic"`).
Analogously for model and base_url.

**End-to-end offline test (non-Anthropic provider path):** `FakeNativeProvider` via
`ValidateAndRetry` → `advise()` → grounded `Advice` with fabrication correctly rejected —
confirmed live in this audit session.

### Core Ask (b) — Full-Library Coverage (all 12 aspects)

**Verdict: SATISFIED**

`_supported` in `build_diagnostics` (`advisor/__init__.py` lines 124–132) contains all
12 aspects:

```
alignment, basis, classification, clustering, depth, fpca,
outliers, regression, regression_cv, represent, smoothing, spm
```

All 12 aspect builder files exist under `python/fdars/advisor/aspects/`:
`alignment.py`, `basis.py`, `classification.py`, `clustering.py`, `depth.py`, `fpca.py`,
`outliers.py`, `regression.py`, `regression_cv.py`, `represent.py`, `smoothing.py`, `spm.py`,
`_utils.py`.

Each builder is wired via lazy import in the `build_diagnostics` dispatcher (lines 154–200).
The dispatcher raises `ValueError("unsupported method …")` for unrecognized methods — no
auto-detection path exists.

Shared machinery — no per-aspect duplication: a single `_system_prompt(task, aspect)` in
`_prompts.py` injects an aspect-specific FDA primer clause from `_ASPECT_PRIMERS` (covering
all 7 new aspects); a single `Advice`/`Recommendation` schema in `_schema.py`; all 36
aspect × task combinations (12 aspects × 3 task families) produce valid prompts.

**Live verification:** `build_diagnostics(np.array([0.4,0.6,0.5,0.7,0.3]), method="depth")`
returned 10 keys including `depth_mean`, `depth_q10`, `depth_q90`; `build_diagnostics(spm_result,
method="spm")` returned 15 keys; `"arl0_t2" not in spm_diag` confirmed True (stochastic ARL
correctly excluded).

## Cross-Phase Connection Verification

### Connection 1: Phase 19 Protocol → Phase 20 Adapters

All 3 Phase-20 adapters implement the protocol surface (`name`, `model`,
`supports_native_structured_output`, `complete_structured`). `_validate.py` and `_protocol.py`
have a single commit predating Phase 20 — not modified by Phase 20. WIRED.

### Connection 2: Phase 20 Adapters → Phase 21 advise()

`advise()` calls `resolve_provider(provider=provider, model=model)` — the factory returns any
of the 4 adapters. `p.complete_structured(Advice, messages, system)` is called uniformly
regardless of provider. `_check_grounding(advice, diagnostics)` fires after, centrally. WIRED.

### Connection 3: Phase 21 Aspect Builders → Phase 22 MCP Surface

`fdars_build_diagnostics` in `server.py` imports `from fdars.advisor import build_diagnostics`
(line 151) and delegates to it. `_DIAGNOSTICS_METHODS` (12-set) mirrors `advisor._supported`;
a drift-lock test (`test_diagnostics_methods_match_advisor_supported`) introspects the
ValueError message to assert exact set equality. Live test confirmed: `represent` via MCP
singleton registry returns 11 keys. WIRED.

### Connection 4: Phase 21 Aspects → Phase 24 Docs

All 12 aspect subsections in `docs/advisor/aspects.md` have builder-derived key tables.
Spot-checks confirmed: fpca 8 keys match `fpca.py`; spm 14 keys match `spm.py` (including
`spe_moment_match_adequate` and `spe_kurtosis_excess`). Two executed fences in the docs page
call only `build_diagnostics` — output confirmed in built HTML (`FDARS_FENCE_OK`). WIRED.

### Connection 5: Phase 22 SKILL.md → Phase 19/20 Provider API

SKILL.md `## Provider Selection` section documents `advise(provider=, model=)` as the sole
provider-selection entry point, lists all 4 provider strings, all 3 env vars
(`FDARS_ADVISOR_PROVIDER`, `FDARS_ADVISOR_MODEL`, `FDARS_ADVISOR_BASE_URL`) matching
`_factory.py._KEY_ENV` exactly, and the Ollama no-key local path. WIRED.

### Connection 6: Phase 23 Matrix Tests → Phase 19–21 Contract

`test_aspect_provider_matrix.py` parametrizes all 12 aspects × 2 provider kinds (native +
fallback) = 24 cells. Each cell calls real `build_diagnostics` then `advise()` via a fake
provider. SDK-leak guardrail asserts `anthropic`, `openai`, `google.genai`, `ollama` all absent
from `sys.modules` after the full matrix run. WIRED.

### Connection 7: MCP LLM-Free Invariant (Phase 22 → Phase 19/20)

`grep -rn "advise" python/fdars/mcp/` returns zero output. `test_mcp_does_not_import_advise`
(runtime file scan) locks this invariant. Provider selection is accessible only through
`advise()` in the Python API, not through any MCP tool. WIRED.
