## Standard Architecture

### System Overview

The v14.0 addition layers a paper pipeline on top of the existing repo without
touching the library. The three existing single-source-of-truth artifacts feed
the paper directly; a new `paper/code/` pipeline re-uses `docs/data/` and the
same `docs_fig` tooling, and a new CI job gates the pipeline before the PDF
compile.

### Structure Rationale

- **`paper/` at repo root, peer to `docs/` and `examples/`:** Keeps the manuscript
  top-level visible and mirrors the convention of other JOSS/arXiv software papers
  (e.g., FDApy arXiv:2101.11003). It is not nested under `docs/` (the paper is not
  a docs page) and not under `examples/` (it is a research artifact, not a tutorial).

- **`paper/code/` not `paper/scripts/`:** The "code" label matches arXiv reproducible-
  artifact conventions. Using `scripts/` would blur the boundary with the repo-level
  `scripts/` directory that serves the docs build.

- **`paper/figures/` committed:** Figures are committed so the manuscript compiles from
  a clean checkout without running the pipeline. The pipeline overwrites them on each
  run; CI verifies the pipeline still runs clean. This mirrors standard practice for
  arXiv submissions (figures committed to the repository).

- **`paper/refs.bib` committed:** The LaTeX compile in CI needs it. It is regenerated
  every pipeline run; the drift tripwire catches stale coverage numbers in the
  manuscript; BibTeX entries are stable once `_references_map.json` is stable.

- **`paper/sections/*.tex`:** Splitting into section files makes diff history readable
  and enables focused phase-by-phase authoring. Each section maps to one roadmap task.

## Architectural Patterns

### Pattern 1: Reuse `docs_fig.py` — Import, Do Not Copy

**What:** `paper/code/paper_utils.py` imports `scripts/docs_fig.py` for the shared
matplotlib rcParams (FDARS_COLORS, hashsalt, Agg backend, `fig()` helper).

**When to use:** All paper figure scripts import `paper_utils` instead of configuring
matplotlib themselves.

**How:** Add `scripts/` to `sys.path` inside `paper/code/paper_utils.py` at the top,
then `from docs_fig import fig, FDARS_COLORS`. The pipeline runner sets
`PYTHONPATH=scripts` as an environment variable (matching the docs build convention
already used by `docs.yml` CI) so the import is unconditional.

**Trade-offs:** Paper figures share the same color palette and determinism settings as
the docs figures — visual consistency with no maintenance overhead. The coupling is
intentional. The only risk is that a docs tooling change breaks the paper pipeline;
since `docs_fig.py` is stable and this project moves docs tooling rarely, this is
acceptable.

**Do NOT copy `docs_fig.py` into `paper/code/`.** A copy diverges silently.

**Difference from docs usage:** The docs pipeline uses `docs_fig.render()` to produce
inline SVG for HTML embedding. The paper pipeline uses a new `paper_utils.save_fig()`
helper that saves as PNG at 300 dpi — required for arXiv submission. The `fig()` helper
is shared; `render()` is docs-only, `save_fig()` is paper-only.

### Pattern 2: Derive Coverage Claims — The Drift Tripwire

**What:** `paper/code/assert_coverage.py` (run as the first step of `generate_all.py`)
reads `_capability_map.json` and `_references_map.json`, derives the coverage
numerator/denominator using exactly the `_coverage_counts()` logic from
`scripts/generate_capability_dataset.py`, then writes `paper/figures/coverage_counts.tex`
and exits non-zero if the file's existing content differs from the derived values.

**This is the drift tripwire.** It mirrors v13.0's derived-denominator pattern: the
manuscript cannot state a stale coverage claim after a new binding or reference is added,
because the pipeline will fail.

**Mechanism — LaTeX macro approach:**

Step 1 — `assert_coverage.py` derives (N, M) and writes:
```latex
% Generated by paper/code/assert_coverage.py — do not edit by hand
% Source: python/fdars/_capability_map.json + _references_map.json
\def\capN{409}
\def\capM{437}
```

Step 2 — `paper/paper.tex` declares the macros at the top:
```latex
\input{figures/coverage_counts.tex}
```

Step 3 — `paper/sections/capabilities.tex` uses the macros:
```latex
fdars exposes \capM{} public callables across 30 functional data analysis
families, of which \capN{} have at least one curated primary-paper entry.
```

Step 4 — If `_capability_map.json` gains new entries (409 -> 410), the next
`generate_all.py` run writes updated `coverage_counts.tex` and exits non-zero,
prompting the author to review, re-commit the updated `.tex` fragment, and verify
the prose in `capabilities.tex` still reads correctly.

**Why not a grep-based check:** The macro approach ensures the LaTeX document itself
cannot contain a stale literal integer — the number in the compiled PDF is always the
derived value, not whatever the author typed.

### Pattern 3: Dataset Reuse — Absolute Path Reference, No Copy

**What:** `paper/code/paper_utils.py` exposes a `data_path(name)` helper that
returns an absolute path to `docs/data/<name>` relative to the repo root. All
figure scripts call `paper_utils.data_path("canadian_weather.csv")` etc.

**Why not symlink or copy:** A symlink inside `paper/` adds OS portability risk
(Windows CI). A copy diverges. An absolute path reference is the simplest correct
approach — the repo is always checked out as a unit.

**Implementation:**
```python
# paper/code/paper_utils.py
from pathlib import Path

_REPO_ROOT = Path(__file__).parent.parent.parent  # code/ -> paper/ -> repo root

def data_path(filename: str) -> Path:
    """Return absolute path to a dataset in docs/data/."""
    return _REPO_ROOT / "docs" / "data" / filename
```

### Pattern 4: BibTeX Generation from `_references_map.json`

**What:** `paper/code/gen_refs_bib.py` reads `python/fdars/_references_map.json`,
emits a standard `.bib` file at `paper/refs.bib`. Each `papers` entry becomes one
BibTeX block. The `callable_index` is not directly used in the BibTeX (it lives in
the JSON for MCP/skill use).

**Schema mapping (from existing `_references_map.json` structure):**
```
papers[key].title      -> title = {...}
papers[key].authors[]  -> author = {A and B and C}
papers[key].year       -> year = {...}
papers[key].doi        -> doi = {...}  (if present)
papers[key].url        -> url = {...}  (fallback if no doi)
papers[key].type       -> "journal" -> @article
                          "conference" -> @inproceedings
                          "preprint" -> @misc with howpublished={arXiv:...}
papers[key].key        -> BibTeX cite key = papers[key] dict key
```

Sentinel papers (keys starting with `_uncurated`) are skipped — same rule as
`_emit_references_page()` in `generate_capability_dataset.py`.

**Drift handling:** `gen_refs_bib.py` is called by `generate_all.py` on every pipeline
run; the committed `refs.bib` is always a regenerated snapshot. No separate drift check
is needed for the BibTeX (the JSON is the SSoT; the `.bib` is purely derived). A stale
`.bib` can only occur if someone edits it by hand — the CI pipeline run overwrites it.

### Pattern 5: Figure Scripts — Seeded, Standalone, Offline

**What:** Each `fig_N_*.py` script in `paper/code/` is a standalone Python script
that, when run, writes exactly one figure file to `paper/figures/`. It never calls
`plt.show()`, always uses `np.random.default_rng(seed=42)` (or a script-specific seed),
and always saves to a fixed output path relative to the repo root.

**Why standalone (not a single monolithic script):** A single big script means one
crash aborts all figures. Standalone scripts can be run individually for debugging.
`generate_all.py` calls each one (via sequential import or subprocess), capturing any
exception and aborting with a clear per-script error.

**Relationship to docs figures:** Paper figures are committed PNGs, not inline SVG.
PNG is required for arXiv submission compatibility. The `fig()` helper from `docs_fig.py`
creates the figure; `paper_utils.save_fig(fig, "fig_01_fdata_tour.png")` saves it as
PNG at 300 dpi. The `docs_fig.render()` SVG path is unused in the paper pipeline.

## Build Order

The build order respects these dependencies:

1. **Scaffold** — `paper/` directory tree, `paper.tex` skeleton, section stubs
   (`sections/*.tex` with placeholder text), `CITATION.cff`. Nothing requires the
   running library; can be done before any code. Sections reference
   `\includegraphics{figures/fig_01_fdata_tour}` but the files need not exist yet
   for authoring to start (LaTeX gives a warning, not an error, for missing figures
   with `\graphicspath` set).

2. **Pipeline infrastructure** — `paper/code/paper_utils.py`, `gen_refs_bib.py`,
   `assert_coverage.py`, `generate_all.py` skeleton. These read the already-committed
   JSON files. At this point the drift tripwire and BibTeX generator are functional.
   `generate_all.py` can be wired with a stub figure list that grows as figure scripts
   are added.

3. **Section authoring + figure scripts** (parallel, by section):
   - Design and Architecture section (`sections/design.tex`): text-only, qualitative.
     Existing docs SVG diagrams can be referenced by description; no new figure script.
   - Capabilities section (`sections/capabilities.tex`): uses `\capN`/`\capM` macros
     set by `assert_coverage.py`. `fig_02_coverage_bar.py` reads `_capability_map.json`
     directly (no fdars import needed).
   - Comparison table (`tbl_01_comparison.py`): generates `figures/tbl_01_comparison.tex`
     from a hand-authored data structure (the comparison data vs scikit-fda/FDApy/R is
     not machine-derived; the script formats it into LaTeX tabular).
   - Case studies (`fig_03..05_*.py`): require compiled fdars; use `docs/data/` datasets;
     produce the most computation-heavy figures.

4. **Pipeline gate** — `generate_all.py` runs all scripts end-to-end. This is the local
   hard gate. Every figure must write its output file and exit 0. The drift tripwire
   asserts coverage counts match the manuscript macros.

5. **CI job** (`paper.yml`) — wired into `.github/workflows/` as a standalone workflow.
   Depends on the pipeline being stable. Placed last because it adds the PDF compile step
   which requires tectonic configuration.

6. **Human manuscript review** — blocking gate before milestone close, matching the
   pattern of human diagram review in v7.0/v10.0/v13.0. The reviewer reads a
   CI-generated PDF, not a locally compiled one. The CI artifact URL is the review
   surface.

## CI Job Placement

Add `.github/workflows/paper.yml` as a standalone workflow, **not** folded into
`ci.yml` or `docs.yml`. Rationale:

- `ci.yml` is the library correctness gate (Rust tests, Python tests across 3.9–3.14).
  The paper pipeline is a different concern; its failure should not block library CI.
- `docs.yml` is the docs site deploy gate. Folding the paper into docs would make every
  docs change trigger a LaTeX compile, which is unnecessary and slow (~22-35 min docs
  build + PDF compile).
- A standalone `paper.yml` with a narrow path filter keeps it out of the hot path for
  normal library and docs development.

**Trigger path filter (paper.yml):**
```yaml
on:
  push:
    branches: [main]
    paths:
      - "paper/**"
      - "python/fdars/_capability_map.json"
      - "python/fdars/_references_map.json"
      - "docs/data/**"
  workflow_dispatch:
```

The `_capability_map.json` and `_references_map.json` triggers ensure the CI job runs
whenever the single-source-of-truth data changes — catching drift the moment a new
binding or reference is added, not just when `paper/` is touched.

## Anti-Patterns

### Anti-Pattern 1: Hardcoding Coverage Numbers in the Manuscript

**What people do:** Write "fdars exposes 409 callables across 30 modules" directly in
`capabilities.tex` as a literal string.

**Why it's wrong:** The count changes whenever a new binding is added. The manuscript
drifts silently. Reviewers see a stale number. The v13.0 grounding pattern (and the
`_coverage_counts()` function in `generate_capability_dataset.py`) was designed
specifically to prevent this.

**Do this instead:** Use the `\capN`/`\capM` macro approach. `assert_coverage.py` writes
`figures/coverage_counts.tex` from the live JSON; `paper.tex` `\input`s it. Coverage
claims in the text use `\capN{}` and `\capM{}` macros — never literal integers.

### Anti-Pattern 2: Running `mkdocs build` as Part of the Paper Pipeline

**What people do:** Generate paper figures by running the full docs build and scraping
the SVG output.

**Why it's wrong:** The docs build takes 22–35 minutes. The paper needs PNG not SVG.
The coupling forces the paper pipeline to depend on the entire docs toolchain.

**Do this instead:** Paper figure scripts are standalone. They import `fdars` directly,
call the same functions the docs examples call, and write PNGs to `paper/figures/` via
`paper_utils.save_fig()`. They are fast (seconds per figure, not minutes).

### Anti-Pattern 3: Committing the Compiled PDF to the Repo

**What people do:** Run tectonic locally and commit `paper.pdf` to `paper/`.

**Why it's wrong:** PDF is binary and bloats git history. Two contributors running
different tectonic versions produce different byte-level PDFs. It is redundant when
CI compiles the PDF reproducibly from committed sources.

**Do this instead:** The PDF is built by CI and uploaded as a GitHub Actions artifact.
The LaTeX source (`paper.tex`) + committed figures + committed `refs.bib` are the
authoritative artifact; any reviewer can regenerate the PDF from them.

### Anti-Pattern 4: Copying `docs/data/` Datasets into `paper/data/`

**What people do:** Copy the six CSV files under `paper/data/` to make the paper
"self-contained."

**Why it's wrong:** Creates a second copy that diverges from the source. Contradicts the
milestone constraint ("reuse existing `docs/data/` datasets without duplication").

**Do this instead:** Use `paper_utils.data_path("canadian_weather.csv")` which resolves
to `docs/data/` at runtime. The repo is always checked out as a unit; the datasets are
always co-present.

### Anti-Pattern 5: Folding the Paper Pipeline into `docs.yml`

**What people do:** Add a `generate_paper` step to the existing `docs.yml` workflow.

**Why it's wrong:** Every docs change (fixing a typo, adding a diagram) triggers the
paper pipeline including the LaTeX compile. The paper is not a docs concern. It creates
false failures when the paper is mid-draft.

**Do this instead:** `paper.yml` is a standalone workflow with a narrow path filter
(`paper/**` + the JSON SSoT files + `docs/data/**`). Completely independent of
`docs.yml`.

### Anti-Pattern 6: Importing `scripts/generate_capability_dataset.py` as a Module

**What people do:** `from generate_capability_dataset import _coverage_counts` inside
`assert_coverage.py`.

**Why it's wrong:** `generate_capability_dataset.py` is a CLI script with top-level side
effects (argument parsing, `sys.exit` calls) and heavy imports (the full fdars package
for introspection). Importing it as a module in a different context is fragile.

**Do this instead:** Re-implement the `_coverage_counts()` function inline in
`assert_coverage.py`. It is ~15 lines of pure dictionary traversal — trivial to
replicate and independently auditable. Add a comment citing the source in
`generate_capability_dataset.py` so future editors know to keep the two in sync.

## Scaling Considerations

This is a one-time research artifact, not a scaled service. The relevant "scale" question
is how the pipeline stays maintainable as the paper grows.

| Growth Scenario | Architecture Response |
|----------------|----------------------|
| New figure added | Add `fig_N_*.py` to `paper/code/`; add call in `generate_all.py`; pipeline reruns in full automatically |
| New binding added (409 -> 410 callables) | `assert_coverage.py` updates `coverage_counts.tex` and exits non-zero; author re-commits the `.tex` fragment and reviews the prose |
| New paper added to `_references_map.json` | `gen_refs_bib.py` picks it up on next pipeline run; `refs.bib` grows by one entry; no manual BibTeX editing |
| Multiple manuscript authors | Section files in `paper/sections/` make per-author diffs readable; `paper.tex` is the integration point |
| arXiv submission | Commit all of `paper/` (tex + figures + refs.bib + CITATION.cff); `paper/code/` included as supplementary material; follow arXiv multi-file upload |
| Journal revision | Update section files, re-run pipeline, push; CI re-validates pipeline and recompiles PDF |
